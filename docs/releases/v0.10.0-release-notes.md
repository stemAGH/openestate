# OpenEstate v0.10.0 — Atomic Booking, Sales Screens and Phone Masking

> The `v0.10.0` tag identifies the released commit. No database migrations and no new
> environment variables. Read **Before you upgrade** and **After you upgrade** below:
> list API responses now mask phone numbers, and two report CSVs need an export
> permission.

## In short

- **Booking is atomic.** A booking, its payment plan and its delay-interest rule are
  created in one transaction, against the GST-inclusive price. A refused plan no
  longer leaves a booking without a plan.
- **No double booking of a unit.** Every unit status change locks the unit first.
- **A new look for the staff app**, and **reworked sales screens**: search and filters
  on Inquiries, a two-column inquiry page, and dashboard counts that open the matching
  list.
- **"Due today" and "overdue" follow the IST calendar day** on any server.
- **Phone numbers are masked in lists and in the API's own log**; detail pages and
  CSV exports keep the full number. The apps stop sending their address as a Referer.
  nginx's access log is not changed on existing installs (a log format to apply is
  included).
- **Tighter handling of sensitive identifier fields** in API responses.

## What's fixed

**A refused payment plan no longer leaves a booking without a plan.** The booking
wizard used to create the booking first and its payment plan in a second request. The
plan step showed and collected amounts against the price *excluding* GST, but the
server requires the installments to add up to the price *including* GST. So the plan
was refused, and the booking was left BOOKED with no plan. Its unit stayed booked, and
booking that unit again was refused.

Now:

- The wizard works out the price first (cost lines with GST) and shows **Total
  payable (GST included)** on the payment-plan and confirm steps.
- A custom schedule is checked against that total as you type, and you can't continue
  until it matches.
- The booking, its payment plan and its delay-interest rule are created in **one
  request**. If any part is refused, nothing is booked, the unit stays free, the
  booking number isn't used up, and the screen says why.
- If the price changes between the preview and booking (for example a GST rate is
  edited in Masters), the booking is refused with the old and new totals.

**Two bookings of one unit at the same moment can no longer both succeed.** Nothing in
the database stopped two active bookings on the same unit. Two bookings made at the
same moment could both succeed, and so could a booking racing a manual block of the
unit, or a transfer into a unit racing a booking of it. Every change to a unit's status
now locks the unit first, so the second request sees the first one's result and is
refused.

**Sales roles no longer get hidden "access denied" errors on the Inquiries pages.**
The pages asked for data those roles can't read (custom-field definitions, and the
user list for sales executives). Nothing visible changes; the pages just stop asking.

## New

- **"Create payment plan" on the installment schedule** of any active booking that has
  no payment plan. Choose a template or enter a custom schedule. A custom schedule
  must add up to the booking's agreed price including GST, shown on the panel.
- **API:**
  - `POST /api/v1/bookings/quote` prices a booking without saving anything. It needs
    `postsales.booking.create`.
  - `POST /api/v1/bookings/with-plan` creates a booking and its plan, and optionally
    its delay-interest rule, in one transaction. It needs `postsales.booking.create`
    and `postsales.plan.edit`, plus `postsales.interest.manage` when an interest rule
    is sent: the same permissions as the separate calls.
- **Upgrade output: two read-only reports** (see **After you upgrade**).

## A new look for the staff app

The staff app has a new visual foundation. Page layouts and behaviour are unchanged.

- On wide screens the sidebar now stays in place while a page scrolls (its menu
  scrolls on its own), and the top bar scrolls away with the page instead of covering
  what scrolls beneath it. On phones the top bar stays at the top, as before.
- One set of colours, spacing, radius and shadows, defined once.
- The Inter typeface (self-hosted, includes ₹), with figures that line up in tables.
- Shared buttons, inputs, cards, page headers, badges and empty states.
- Accessibility:
  - every icon-only button has a name, and there is a visible focus ring and a
    "Skip to main content" link;
  - text and control colours meet WCAG contrast.

Dark-mode colours are defined but not switched on yet.

## Sales screens

- **Inquiries list:**
  - A search box (name, phone or email) and filters for status, temperature, project,
    follow-up due (today or overdue) and, for managers, owner.
  - The filters are kept in the address, so a link or the back button reopens the
    same view.
  - New columns: next follow-up ("Today" or "2 days overdue", with the date), owner,
    and Call and WhatsApp buttons on every row.
- **Inquiry page:**
  - The follow-up form sits beside the details (above them on a phone), with the
    history newest first.
  - Status buttons read "Mark as Continued" and so on, and the page has Call and
    WhatsApp buttons.
  - Reassign shows only for people allowed to reassign.
- **Dashboard:** the greeting uses your name, and each count opens the list filtered to
  exactly what it counts.
- **Dates on these screens** are shown as DD-MM-YYYY, in India Standard Time.

### Dashboard counts can move at midnight IST

"Follow-ups due today", "Overdue follow-ups" and My Day now count by the **IST calendar
day**, on any server. They used to use the server's own time zone.

- **On a server set to IST:** nothing changes.
- **On a server set to UTC (or anything else):** the counts used to roll over at the
  server's midnight (05:30 IST for UTC). They now roll over at midnight IST, and match
  the new follow-up filter on the Inquiries list exactly.

### Inquiries API

- `GET /api/v1/inquiries` takes `search`, `status` (one or more, comma-separated),
  `temperatureId`, `projectId`, `assignedToId` and `followUp` (`today` or `overdue`).
  Same permission as before (`presales.inquiry.read`), and a filter never shows a lead
  outside your team.
- **Stricter:**
  - Unknown query parameters are now refused (400).
  - `sortBy` accepts only `createdAt` and `nextFollowupAt`.
  - An API client that sent anything else got it silently ignored (or a 500 for an
    unknown `sortBy`), and now gets a 400 that names it.
  - `search` was accepted before but ignored; it now filters.

## Phone numbers are masked in lists

Every screen and API response that lists many people now shows only the last 4 digits
of a phone number (`••••••3210`). Detail pages, PDFs and CSV exports keep the full
number.

- **Screens:**
  - Inquiries, My Day, Applicants, Brokers, the duplicate warning, and the applicant
    pickers in the booking wizard and Receipt Entry.
  - The audit log, communications, dispatch history and pending change requests.
  - The on-screen pre-sales Inquiries Export, the birthday list and the broker dues
    report.
- **Call and WhatsApp in lists:** pressing one fetches the number from the inquiry's
  own record, with the same permission and team scope, so the list never carries it.
  Call opens your phone app. WhatsApp opens a new tab.
- **API change for integrations:** list endpoints now return masked values in
  `primaryPhone`, `primaryPhoneNormalized`, `alternatePhones` and `phone` (and
  `toAddress` / `recipientAddress` for SMS):
  - `GET /inquiries`, `/inquiries/my-day`, `/applicants`, `/applicants/:id/duplicates`,
    `/brokers`, `/users` and `/audit`;
  - the `possibleDuplicates` in `POST /inquiries`;
  - communications, dispatch history and `/admin/change-requests`;
  - the JSON form of the reports above.

  Read a single record (`GET /applicants/:id`, `/inquiries/:id`, `/brokers/:id`,
  `/users/:id`) for the full number. Search by phone still works on the full number.
- **CSV downloads need `presales.report.export`:**
  - It already applied to the pre-sales exports. It now also applies to the birthday
    list and all broker reports, and each download writes an audit row.
  - Every standard role that can view those reports already holds it.
  - **Custom roles** that view the birthday list or the broker reports need it too,
    or the CSV button is refused.
  - The on-screen view of every report is unchanged and needs only the view
    permission, as before.
- **Logs.** A phone number typed into a search box travels in the request's address,
  and the staff app also keeps its search in its own address. What this release masks,
  and what it doesn't:
  - **Masked: the API's own request log** (the `openestate-api` service's journal),
    in the request URL, the query values and the `Referer` header.
  - **No longer sent: the `Referer` header.** The staff app and the portal now tell
    browsers not to send their address with requests (`Referrer-Policy:
    no-referrer`). Their addresses can hold a phone search or a reset or invite
    token.
  - **Not masked: nginx's access log on existing installs.** nginx's default log
    format records the full request line, query string included. The upgrade doesn't
    change your nginx configuration; see **After you upgrade**, item 4, for a log
    format you can apply.
  - **Logs from earlier releases may contain phone numbers from search URLs** (for
    example `GET /api/v1/applicants?search=98765…`), and reset or invite tokens in
    referers, in both the API's journal and nginx's access log. Treat them as
    personal data under your retention rules.

## Sensitive identifier fields in API responses

This release tightens how sensitive identifier fields appear in API responses. Only
the masked value of an identifier is returned, on every endpoint, and new audit entries
no longer store internal identifier fields. Stored audit entries are unchanged; these
fields are left out when they are shown. No action is needed, and no screen changes.

## Deprecated

- **`POST /api/v1/bookings`** still works for API clients, but creates a booking with
  no payment plan. Use `POST /api/v1/bookings/with-plan`. The separate
  `/bookings/:id/plan/...` endpoints stay.

## Compatibility

Compared with v0.9.1:

- **Database and setup:**
  - no database migrations;
  - no new environment variables;
  - no new infrastructure requirements.
- **Roles:** no changes to roles or the permissions they hold.
- **What existing permissions allow:** the birthday-list and broker-report CSVs now
  also need `presales.report.export` (see above).
- **API behaviour changes for integrations:**
  - list endpoints mask phone numbers;
  - `GET /api/v1/inquiries` refuses unknown parameters and unknown `sortBy` columns;
  - `POST /api/v1/bookings` is deprecated (it still works).
- **Money:** no change to financial calculations or ledger behaviour. The atomic
  booking path uses the same pricing code, checked against the original on 2,000
  generated bookings.

## Before you upgrade

- **Integrations and scripts:**
  - If they call `GET /api/v1/inquiries`, check they send only the parameters listed
    above.
  - If they read phone numbers from list endpoints, they must read the single record
    instead.
- **Custom roles:** if any can view the birthday list or the broker reports and must
  download their CSVs, add `presales.report.export` to them.

## Upgrading from v0.9.1

From the server's source folder, with the release tag:

```bash
cd /opt/openestate-src/deploy/native && sudo ./upgrade-native.sh --ref v0.10.0
```

Use the tag or a full commit SHA, never a branch name, and keep the automatic
pre-upgrade backup on (don't pass `--no-backup`). Afterwards
`curl -s http://127.0.0.1:3000/api/v1/health` reports `"version":"0.10.0"`.

Upgrading from an older version: read the v0.9.0 and v0.9.1 release notes first; this
release adds nothing to their upgrade steps.

## After you upgrade: what to check

1. **Read the two new reports in the upgrade output.** They are printed per company and
   change nothing.
   - **"Payment plans: N active booking(s) have no payment plan"**, followed by their
     booking numbers. These are most likely bookings left by the old wizard. For each
     one, open its installment schedule (Post-sales → the booking) and either:
     - **Create payment plan**, so the installments add up to the agreed price
       including GST shown on the panel; or
     - **Cancel Booking** if it was never meant to stand. This releases the unit.
       Nothing was received on such a booking, so nothing is refunded.
   - **"Units: N unit(s) have more than one active booking"**, followed by the unit and
     its booking numbers. This could only happen through the race fixed in this
     release. For each unit, decide which booking stands (check receipts first), then
     cancel the other booking, or transfer it to a free unit, from its installment
     schedule.

   If a count is 0, there is nothing to do.
2. **Custom roles and CSV downloads.** In Admin → Roles, check every custom role that
   can view the birthday list or the broker reports. If its users download those CSVs,
   it needs `presales.report.export`. Standard roles need no change.
3. **Integrations that read phone numbers.** Check anything that reads phone numbers
   from a list endpoint (or from the JSON form of a report). Those now get
   `••••••3210`. Read the single record for the full number.
4. **nginx's access log.** The API's own log now masks phone numbers, but nginx's
   default log format still records the full request line, including a search's
   query string. Upgrades don't touch your nginx configuration (only the first
   install writes it). To log request paths without their query strings:
   - Create `/etc/nginx/conf.d/openestate-log.conf` with:

     ```nginx
     # The request path without its query string, and no referer.
     log_format openestate_paths '$remote_addr - $remote_user [$time_local] '
                                 '"$request_method $uri $server_protocol" '
                                 '$status $body_bytes_sent "-" "$http_user_agent"';
     ```

   - In `/etc/nginx/sites-available/openestate`, inside the `server { … }` block, add:

     ```nginx
     access_log /var/log/nginx/access.log openestate_paths;
     ```

   - Check and reload: `sudo nginx -t && sudo systemctl reload nginx`.

   A later release will apply this automatically.
5. **Logs from earlier releases.** They may contain phone numbers from search URLs,
   and reset or invite tokens in referers, in the API's journal and nginx's access
   log. Handle them under your retention rules.
6. **The dashboard on a non-IST server.** "Due today" and "overdue" now roll over at
   midnight IST. Expect the counts to change at that time, not at the server's
   midnight.
